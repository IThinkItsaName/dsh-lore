# 设计文档地图

这里放的是**设计权威**：改了实现就要改对应规格，`docs/` 里的每一份都在
`tests/audit-doc-consistency.mjs` 的审计清单里（改名前它只审计 `worklog-spec.md`，
另外三份——包括记忆规格——不受任何门禁约束，这正是本仓库反复出现的那类失效）。

同一份 harness 现在还管**技能层**的文档：`skills/project-work-log/SKILL.md` 与
`references/` 下的五份。两套语料按**各自的权威**审计——插件文档对插件（环境变量、配置键），
技能文档对它描述的那个 CLI（`journal.py` 的子命令与文档互链），详见该 harness 的文件头。

**规格与使用说明的分界**：`docs/` 是给**维护者**看的「为什么这样设计」；
包根下那几份是给**使用者 / 维护者**看的「怎么用、怎么发」：

| 包根文档 | 给谁 | 管什么 |
|---|---|---|
| `README.md` | 使用者 | 门面：三块能力（技能层 / 记忆层 / 插件层）、怎么装、怎么用。**细节一律链出去，不复制** |
| `SETTINGS.md` | 使用者 | 插件配置的权威：字段、默认值、要不要重启、两个设置面的分界 |
| `RELEASING.md` | 维护者 | 发版清单：三处源/副本的**固定方向**、检查点、打 tag |
| `PUBLISHING.md` | 维护者 | 仓库怎么建（一次性） |

两者都要改，但改的理由不同。**`README.md` 的门面说法与 `plugin-spec.md` 的架构说法要对得上**：
门面讲"三块能力"，架构讲"四层"（运行时层 + 配置层合起来就是门面说的插件层），
两边不一致时以本目录的规格为准。

| 文件 | 管什么 | 不变量 |
|---|---|---|
| [worklog-spec.md](worklog-spec.md) | 记录体系本身：分册、编号、精细度档位、`check`/`lint` 的判定 | 记录格式与门禁语义 |
| [settings-spec.md](settings-spec.md) | 配置卡片：三页签、每个字段的归属（装载期 vs 用时现读）、写回通路与两个落点 | 哪些改动需要重启 |
| [memory-spec.md](memory-spec.md) | 全局记忆：目录布局、来源分档、索引、`dream`、`inbox`、升格 | 准入靠来源分档，不靠重要性 |
| [goals-spec.md](goals-spec.md) | `目标.md`：长期目标 → 阶段的两层表 | 目标只增不改 |

## 三条跨规格的规矩

1. **规格与实现不一致时，先查是哪个错。** 本项目已发生多次「规格说 A、实现是 B」，
   每次都是人读出来的，不是测试查出来的——所以 `docs/` 才被纳入审计清单。
   修正时**改规格还是改代码，要看哪边是对的**，并在记录里写下这次判定。
2. **规格里不写会过期的具体数字**（行数、文件大小、提交号）。要举实例就指向文件与函数名。
3. **一处事实只有一个家。** 设置字段的权威在 `settings-spec.md`，记忆准入的权威在
   `memory-spec.md`；`README.md` 只讲怎么用，需要细节时**链过去**，不复制一遍。
