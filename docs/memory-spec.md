# 全局记忆规格（可配置的记忆根）

> **状态**：已批准，实现中。
>
> 这是把 worklog 的**经验层**延伸到工作区之外的一层：让一个工作区里确证过的教训，
> 能在**另一个**工作区被用到；让与工作区无关的通用知识也有处可放、且**不冒充已验证**。

## 零、记忆根放在哪（2026-10-14 改）

**默认落在 `<用户主目录>/dsh-lore-memory/`，不再挂在 `$DSH_HOME` 下**；位置**可配置**。

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `--memory <路径>` | CLI 显式参数（也是 harness 的隔离手段） |
| 2 | 设置里的 `memoryDir` | 设置卡片的「记忆存放位置」；`<DSH_HOME>/worklog/settings.json` 是同一件事在无 `configEditor` 宿主里的落点 |
| 3 | `$DSH_WORKLOG_MEMORY` | 逃生舱（保留给测试与兼容） |
| 4 | 默认 `<用户主目录>/dsh-lore-memory` | 相对路径按**用户主目录**解析（与技能目录不同，那两栏按包根算） |

**为什么不再放 `$DSH_HOME` 下**（旧版三条理由的重新裁决）：

| 旧理由 | 现在怎么看 |
|---|---|
| 记忆是**跨插件的公共知识** | **仍然成立**，而且更强：它连 harness 都不该绑 —— 跟着 `$DSH_HOME` 走意味着换一次安装位置/换一个 harness 就换个库 |
| **卸载不该带走记忆** | **仍然成立**：所以也不放进插件自己的目录；新默认位置同样在插件之外 |
| 与既有约定一致（`profiles/`、`sessions/` 都在 `$DSH_HOME`） | **不再采纳为理由**：那些是**宿主自己的状态**，而记忆是**与 agent 无关的知识**。两者的归属不同，放在一起只是省事 |

**一次性迁移**：首次解析时，若**新根为空**且**旧根 `<DSH_HOME>/memory` 有内容**，
把旧根整份**复制**过去并写一个 `.moved-from-dsh-home` 留痕；**旧根绝不自动删除**
（跨卷 rename 会失败、删了不可回滚），日志与设置页都会说明"旧记忆仍在原处，确认后可自行删"。
判定与实现见 `lib/index.js` 的 `migrateMemoryIfNeeded()`；已经迁过（有标记）或新根非空即不再动。

**它要花多久、占多少盘**（2026-10-15 实测，`lib/index.js:914-922` 在**装载路径上同步**跑
`copyTree()`，含 `.git`）：约 **0.13 ms/KB** —— 4 MB / 2000 文件 ≈ **0.57 s**，
40 MB 的老库 ≈ **5–6 s** 的首次启动停顿；迁完**磁盘占用翻倍**（源根故意不删，等你确认后自己删）。
所以"老根多大 = 首次启动多等多久"是可以先算出来的；第二次挂载只读标记，≈ 0.03 ms。
**不把拷贝挪到后台**是有意的：那会破坏"什么都没动、可核实"这条被测试钉着的性质。

**它仍然不放进插件自己的目录**：卸载本插件不该带走记忆 —— 这条从第一版起没变。

## 一、分层

| 层 | 位置 | 进注入？ | 谁读 |
|---|---|---|---|
| 工作区记录 | `<工作区>/work_log/` | 否 | 智能体（工作区内文件工具） |
| 工作区经验 | `<工作区>/work_log/lessons/` | 否 | 智能体 |
| 发布清单 | `<工作区>/work_log/发布.md` | 否 | 全局层工具（**唯一**获准读的工作区文件） |
| 项目摘要 | `<工作区>/work_log/摘要.md`（dream 产出） | 否 | 智能体 |
| **全局记忆** | `<记忆根>/`（默认 `<用户主目录>/dsh-lore-memory/`，见 §零） | 只注入索引一笔 | **只能通过工具** |
| **全局技能** | `<DSH_HOME>/skills/` | 目录（名字+描述） | 技能注册表（**现成能力，非新建**） |
| 常驻规则 | 根 `AGENTS.md` | 是 | 宿主 |

**为什么智能体不带工具就读不利索**：`ctx.workspaceFiles` 把它的 `read`/`grep` 限制在
工作区内（"files **inside** a Session's workspace root, confined by lstat,
containment, and a stat re-check"），而 `ctx.tools.register` 注册的工具
**在宿主进程内执行**，读哪儿由它自己定。所以记忆经**工具**访问是正路；
在 `workspace-write` 之下 `read` 说不定也能读到（读不限、写受限），但那是策略的恩惠、不是契约。

## 二、目录布局

```
<记忆根>/                      默认 <用户主目录>/dsh-lore-memory/，可用设置或 --memory 换
├── .git/                    只跟踪未被排除的
├── .gitignore               排除 personal/ 与 inbox/
├── INDEX.md                 注入用索引（**生成物，不手写**）
├── workspaces.json          名册：路径 / applies-to / read / upload / 最后发布
├── candidates.json          候选：知存在、未登记（**只提示，不自动收录**）
├── .state.json              机器生成，两段：各工作区清单的摘要哈希 + `usage`（命中计数）
├── 01-<领域>.md             正文分册
├── personal/                个人内容：不进 git、不进索引、不被默认检索
├── inbox/                   跨工作区信箱：不进 git，阅后即删/转移
└── feedback/                工作区使用评价：**不是记忆条目**（见下），进 git
```

**`feedback/` 不是记忆**：`memory_volumes()` 只认"直下一级 + 形如 `NN-<领域>.md` + 是文件"，
所以这个目录既不进 `INDEX.md`、也不被 `memory search` 命中、更不参与 `memory lint`。
`<记忆根>/feedback/<工作区名>.md` 由 `memory collect` 从各工作区发布清单里 `feedback:` 声明的那份文件
**镜像**进来（**正文逐字不动**，只在前面加一层出处头：说明它不是记忆条目、来源、收集时间）。
**它进 git**（与 `personal/`、`inbox/` 相反）—— 它是**可审阅的公共反馈**，用途是"根据真实使用改进"，
不是"被检索的知识"。所以**指望被自动读到的内容不要写在这里**，那是正文分册的事。

**为什么统一一个根**：检索、索引生成、lint 只需遍历一处；"不进 git"用 `.gitignore`
精确表达即可，不必开平行顶层目录。

**为什么必须进 git**：`$DSH_HOME` 不被任何东西同步，删一次就没了；
而"能 `git diff`"正是**你审阅"谁想进来"**的机制 —— 那是唯一可能造成污染的动作。

## 三、条目格式

正文分册里**一条一段**：

```
- id: <slug>
  applies-to: <标签, 标签>
  state: active | stale | retired
  source: <分档，见下>
  cited-by: [<工作区>, …]        ← 生成，不手写
  <一句话教训：症状 → 根因 → 做法>
```

字段规则：

- `id`：**全局唯一**，`[a-z0-9-]`，不带空格。
  **同名是否算冲突，取决于分册（见下）** —— 因为"另一个工作区引用同一个 id"与
  "两个工作区碰巧起了同一个名字"在数据上长得一样，只有分册能把它们分开。
- `cited-by`：**工作区名字**的列表，由工具维护，手写不算数。
- `applies-to`：逗号分隔的标签。留空表示"到处都适用"。
- `state`：三态之一，缺省 `active`。
- 正文一行：`症状 → 根因 → 做法` 的形状最好用，但不强制。

### 同名 id：引用还是撞名

`cited-by` 想记录的是"**别的**工作区也引用了这条"，而那件事**只能通过另一个工作区在清单里
发布同一个 id 来表达**。于是同一个 id 有两种截然不同的含义，靠**分册**区分：

| 情形 | 判定 |
|---|---|
| 同一个 id 出现在**同一个分册**（同一标签域） | **引用** —— 合并进 `cited-by` |
| 同一个 id 出现在**不同分册** | **撞名** —— `collect` 报错退出，要求改成更具体的 id |

这条是规格原先的矛盾之处：早先写"两个工作区发布同名 id 会被拒绝"，与"被别的工作区引用要
累计进 `cited-by`"**不可能同时字面成立**。分册就是那把区分尺。

### `wl/NNNN` 能核到什么程度：**这是单向的门**

`发布.md` 是全局层**唯一**获准读的工作区文件，所以：

| 引用形式 | 能机械校验什么 |
|---|---|
| `wl/NNNN`（本工作区），或 `<本工作区名>/wl/NNNN` | **该篇号在本工作区的记录目录里真实存在** —— 所以"记录被删掉"能被抓住 |
| `<别的工作区>/wl/NNNN` | 只能核到"**它的清单点了这个引用**"。那个工作区的记录**读不到**，所以无法核到记录本身 |

**这是设计的结果，不是实现的偷懒**：单向的门 = 一个工作区的内容只能由它自己交出来。
规格原先写"`wl/NNNN` 必须真实存在（机械校验）"，跨工作区时**做不到**，现在按上表说清。

`wl/1` 与 `wl/0001` 都接受，解析后规范化为 `wl/0001`。

## 四、来源分档（准入的核心）

**准入靠分档，不靠"看起来重要吗"** —— 后者等于预测未来，而且会系统性地偏向
"听起来宏大的话"，正好与实战教训相反。

| `source` | 准入 | 进索引 | 附加要求 |
|---|---|---|---|
| `<工作区>/wl/NNNN` | 允许 | 是 | 该篇号必须**真实存在**（机械校验） |
| `manual:tested` | 允许 | 是 | 正文须写清**怎么验的**（命令 / 数字 / 结果） |
| `manual:read` | 允许 | 是 | 正文须**指名出处**（哪个文件、哪一节） |
| `manual:inferred` | **允许** | **否** | **强制标注"未经证实"**；正文写推断依据 |
| 无 / 认不出 | **拒绝** | — | — |

> **为什么留 `inferred` 一档而不是堵死**：堵死的结果不是"没有推断"，
> 而是**推断被伪装成"读过"**。留一档并强制标注，比如下更安全 ——
> 这与本项目"错误的机制比没有机制更糟"的既有判断一致。

## 五、发布清单（`<工作区>/work_log/发布.md`）

工作区**唯一**获准被全局层读取的文件，也是**双向白名单**：不在清单里的教训
永远不会离开那个工作区。

```
applies-to: dsh-plugin, python-stdlib-tooling
upload: true
feedback: 评价-worklog.md

- wl/0001  样式被别的插件认领  →  id: host-style-claiming
```

- 清单头两行是**本工作区的声明**：它关心哪些标签（供注入取交集）、是否允许上传。
- 每一条点名"哪条教训允许外流"，并可给一个建议 id。
- `upload: false` 或缺清单 → 视为**只读不传**（合法且常见的默认）。
- **可选 `feedback: <路径>`**：**工作区使用评价**文件（相对容器；也接受绝对路径）。
  它不是教训、**不进正文分册**；`collect` 把它**原样镜像**到 `<记忆根>/feedback/<工作区名>.md`
  （正文逐字不动，只加出处头），并**按内容幂等**：清单与评价都没变才跳过，**只改评价也会被收到**。
  它和教训受**同一道白名单**管：`upload: false` 时评价也不收；声明了但文件不在 → `collect` 报问题
  （与"坏引用"同规格）。镜像文件的正文由工具**覆写** —— 要改请改工作区里那份。

## 六、注入（两套接口，按易变性分工）

| 内容 | 接口 | 理由 |
|---|---|---|
| 全局记忆索引 | `ctx.systemPrompt.section({…})` | 稳定；进系统提示词当固定前缀 |
| **待收 N 条** | `ctx.systemPrompt.context({…})` | **可变；尾注入** |

宿主文档对后者的定义是 "cache-safe counterpart to `PromptSection`"，
其快照"logged … **after** retained model history **only when it changed**"。

- 两处的 `text` 都用**函数形式**（每次装配求值）→ 相应设置项**改完立即生效**。
- 计数为 0 时 `text` 返回空串（空串不贡献）→ 没消息时一行都不出现，且不变时**零快照**。
- **预算按字计不按行计**：一行的长度可以差十倍，按行限等于没限。
  软目标 `MEMORY_INDEX_SOFT_CHARS`（提示该收敛）、硬上限 `MEMORY_INDEX_HARD_CHARS`（`lint` 报错）。
  **超限报错，绝不静默截断** —— 静默截断会让记忆悄悄变得不完整。

## 七、生命周期与长期价值

**`memory collect` 不重建索引** —— 索引是**生成物**，只有 `memory index` 会写它。所以
`collect` 之后 `lint` 会一直是红的，直到你跑一次 `memory index`。这是刻意的：一个命令只做一件事，
"收集"与"重新生成索引"混在一起会让两者都难排查。`collect` 会在结尾提示这一点。

**幂等的判据是"内容"**：`.state.json` 里每个工作区存**两枚摘要** —— 发布清单的、以及（若声明了）
`feedback:` 那份评价文件的。**两枚都没变**才跳过；只改评价也会照收。评价的镜像**正文没变就不重写**
（否则每次 `collect` 都会因为出处头里的收集时间而改写文件，把"幂等"和"这份文件只在源变了时才动"一起破坏掉）。

**入场时不判断"长期价值"** —— 那等于预测未来。入场只做两件机械事：
来源分档合法 + 发布清单点名。

| 事后信号 | 价值 | 动作 |
|---|---|---|
| **被别的工作区引用** | **最强且无法伪造** —— 它真的跨了工作区 | 排序**前置**；累计进 `cited-by` |
| **被修订（记下"被什么取代"）** | 冲突已消化，信息密度更高 | **唯一自动降级**：`active → stale` |
| 被检索命中 | **弱且危险** | 只用于 `lint` **建议**审阅，**绝不自动降级** |

> **只会在极罕见情况下救命的教训，命中次数天然是 0，而它可能最珍贵。**
> 用命中次数降级会系统性删掉最珍贵的保险、留下最常被问的常识。

**三态**：`active`（进索引）/ `stale`（不进索引，仍可搜）/ `retired`（默认搜不到，**文件永不删**；
在 `lint` 里**只判结构**，见 §八）。

**成长压力在索引，不在条目数**：索引大小 ≈ 相关领域数 × 每领域条数，与总条目数
**非线性**。所以只解决"索引可扫读"，不对总条目数设上限。

## 八、校验（`memory lint` / `memory index --check`）

| 判据 | 级别 |
|---|---|
| 来源合法且可分档；`wl/NNNN` 能指到真实记录 | ERROR |
| `manual:inferred` **不得出现在索引**中 | ERROR |
| `manual:inferred` 正文**缺「未经证实」标注** | ERROR |
| `manual:read` 未指名出处 / `manual:tested` 无可核对结果 | ERROR |
| `id` 唯一；`applies-to` 合法 | ERROR |
| `cited-by` 里的工作区名**不在名册里** | ERROR（同名不同路径 → WARN，因为名字无法区分） |
| 索引与正文一致（漏生成 / 多出条目） | ERROR |
| 注入段超**硬上限** | ERROR |
| 分册标题/标签与文件名不一致 | WARN |
| 近似重复（标题规范化 + 正文 trigram 过阈） | WARN（`--strict` 才 ERROR） |
| 长期未命中 / 够条件可升格 | INFO（仅建议） |

沿用本项目既有的"启发式不判死刑"规矩：**判不准的一律 WARN，`--strict` 才 ERROR**。

> **退役条目的例外（2026-09-30 起）**：`state: retired` 的条目**只判结构** —— `id` 唯一且合法、
> `applies-to` 合法、`state` 是三态之一；**不判来源与名册、不判 `manual` 档的正文要求、
> 不参与近似重复**。理由：§三 说退役的语义是"默认搜不到、**文件永不删**"，而工作区与记录
> 都会消失 —— 若内容要求照判，一条退役条目会因为来源工作区没了（**正常生命周期**）或正文
> 本就不合格而**永久报错**，用户想让门禁变绿就只剩删文件一条路，与"文件永不删"直接冲突。
>
> **跳过是按 `state` 判的，不是"不判了"**：同一条改成 `active` 之后，来源与内容要求照旧生效。
> 这两件事各有断言钉着（`_selftest.py` 的 6c 小节），也各有变异守着。

## 九、名册与许可

| 规则 | 说明 |
|---|---|
| `read` 默认 `true`、`upload` 默认 `false` | "只看不给"合法且常见 |
| 未登记的工作区 | **不参与**。工具**无法自行发现工作区**（没有跨工作区读权限），所以沉默 = 不参与 |
| `candidates.json` | **只提示**（`memory status` 报"有 N 个候选未登记"），**不自动收录** |
| 候选从哪来 | 工具只能看见它**被显式给到的** `[ROOT]`，所以候选就是：命令行给过、有清单、但**没登记**的工作区（`collect`/`status` 记下它，`publish` 清掉它） |
| 名册隔离 | 设置页的状态块只显示计数，不列路径 |

## 十、dream 的两种模式，与命令面

`dream` 是**两半**：脚本做机械的那半，模型做归纳的那半。所以它有两个模式，而不是一个
"自动整理"按钮：

| 模式 | 谁用 | 行为 |
|---|---|---|
| `dream [ROOT]` | 脚本 | 已经收敛的记录从 `<容器>/摘要.md` 的记录链接算出**未覆盖**的那些，按主题分组，发骨架到 `<容器>/摘要.draft.md` |
| `dream --accept [ROOT]` | 收下模型填好的骨架 | **先机械校验再写回**；过不了就拒绝，`摘要.md` 保持不变 |
| `dream --check [ROOT]` | 以后复查 | 回指**现在还指得到吗** |

**为什么是标志而不是子命令**：`argparse` 不允许在子解析器前面放一个可选位置参数 ——
实测 `dream <路径>` 会被当成子命令名而失败。互斥标志同时也让语法与"一个 `dream` 命令、
三种用法"的说法一致。

**回指必须是 markdown 链接**（如 `[0001-a.md](0001-a.md)`）。原因很实际：校验**复用既有的
死链检查器**（`check` 用的那一个），而不是另写一套 —— 所以"摘要能不能下钻"与"文档链接有没有
断"用的是同一把尺。

### 命令面

```
memory publish | collect [--dry-run] | add | search | index [--check] | lint [--strict] | status
dream [ROOT] [--dry-run] [--force] | dream --accept [--in FILE] | dream --check [--strict]
inbox put [--text T | --file F] [--thread ID] | list [--json] | take NAME [--into-record TITLE] [--keep]
inbox sweep [--older-than N] [--apply] | count
inbox subscribe [--off] | unsubscribe | status            # 收件方的主动送达授权（[ROOT] 是工作区）
promote suggest [--all]
```

**位置参数顺序有个坑**：既收自由文本/名字、又收 `[ROOT]` 的子命令里，**自由参数必须声明在前面**
（`memory add "<教训>" … [ROOT]`、`inbox take NAME … [ROOT]`），否则 `argparse` 会把 `[ROOT]`
先吃掉。`--memory` 只挂在子解析器上、不挂父解析器：两边都挂会让子解析器的默认值**静默覆盖**
父级的 `--work-log`。

**`inbox count` 的契约**：**只打印一个整数，一行，别的什么都没有** —— 插件按行取它，
所以任何多余的输出都会破坏调用方。

## 十一、跨工作区消息：两种送达模式

信箱**不是记忆**，是通信 —— 生命周期与可见性都和记忆相反（不进 git、不进索引、阅后即删）。

### 两种模式

| 模式 | 机制 | 何时用 |
|---|---|---|
| **被动**（默认） | `PromptContext` 尾注入一行「待收 N 条」，等收件方下次开会话或自己来查 | 绝大多数情况 |
| **主动**（逐工作区显式开关） | 收件方在自己的工作区跑 `journal.py inbox subscribe`（写 `<记忆根>/inbox-subscriptions.json`：固定 `session` id + 已推送条数）。发件方 `worklog_memory` 的 `send` 带 `to` 时：`ctx.sessionController.create({ cwd, sessionId })` → `resolveAgent(sessionId)` → `agent.followup(createUserMessage(...))`（与 `dsh-schedule` 同一条投递路）→ `sessions.flush`，推的是**不含正文**的提醒 | 确实需要对方**现在**动起来 |

**主动模式的代价必须写在这里**：它会在你不在场时**花额度**、并且**在没有上下文的情况下自作主张**。所以它默认关，且是**收件方工作区**的授权，不是发件方能决定的。

### 六条设计规矩

1. **权限跟着收件方**。消息**永不携带**沙箱模式；自动拉起的会话沿用目标工作区的**当前策略**。
   `sandboxPolicy.resolve()` 的语义是「用户批准的显式模式 > 会话最后一次 `sandbox/mode` 事件 > 部署默认」，
   而 `CreateAgentOptions` / `CreateSessionOptions` **根本没有沙箱字段** —— 所以"发消息就让对方 full-access"
   意味着**任何工作区都能让另一个提权**，这与"单向的门"直接矛盾。需要提权就在**那个工作区**改策略。
2. **跨工作区投递只到工作区粒度**：`send` 只表达意图（"这条给 X 的收件箱"），
   **放进哪个会话由收件方决定**；`send.session` 只接受**本工作区**的会话 id。
   （2026-10-18 起 `sessions` 可显式 `scope: "all"` **只读**列出其他工作区的会话并标注归属；
   那是查询能力，不是投递能力 —— 投递仍走这一条。）
   （这条只管**跨工作区**；同一工作区内的会话是用户自己的，见本节末「2026-10-17 重新明确」①。）
3. **收件会话可复用，且应当复用**。一个工作区一个固定的「收件箱会话」，用**固定 id** 幂等获取
   （命中就 `resume`，不存在才 `create`）—— 于是"每来一条就新建一个"从设计上不可能发生，
   也避免"把该工作区所有 session 都拉起一遍"。
4. **消息是不可信的 `user/message`**。明确**禁止**写成 `developer/message` 或 `system/message`：
   那会把另一个工作区的文字**提升成指令**。它是一条"来自 X 的消息，等你看"，受**收件方**策略约束。
5. **被动模式也只注入计数，正文永不进提示词**。宿主在尾部运行时上下文里加的只有一行
   「工作区信箱里有 N 条跨工作区消息待查看」（空信箱返回空串 —— 什么都不加，而不是加一句"没有消息"）；
   正文要收件方自己去取。理由：自动进上下文等于把**别人写的文字**
   当成上下文的一部分，而它其实是外部输入；把它留在"要不要去取"这一步，决定权才在收件方手里。
   配套的机械痕迹：`put` 落盘时写 `from` / `at` / 「不可信输入」头部，`list` 显示 `from`、
   `take` 把整段渲染出来 —— 于是规矩 4 那条"消息不可信"在**被动模式下也不是一句口头约定**。
6. **收件会话会长期增长**，所以它需要自己的收束规则。**已实现（2026-10-17）**：每成功推送
   一条提醒就 +1，到 `INBOX_SESSION_ROTATE_AFTER`（40）条时换一个新的收件会话 id；旧会话
   原样留着，由用户自己归档（不删、不清空）。计数写在授权表里，**只有真的推进去了才 +1**
   —— 失败不记账，下一次还会再试。**没实现的那半**：按时间收敛（"超过 N 天没动过就换"）
   没做；现在的判据只有条数。

### 取件：正文以**文件**进收件方工作区，而不是以文字进提示词

2026-09-30 起，插件工具（`worklog_memory` 的 `inbox` 操作）是收件方取件的**主路**：

- 不带 `message`：列等待中的条目，**只给元信息**（名字 / `from` / 大小 / 年龄）—— **正文一律不给**；
- 带 `message`：把**那一个文件整个搬进**收件方工作区（`<工作区>/.lore-inbox/`），返回落点路径。
  之后用什么读、怎么处理，都在工作区里用普通文件工具做。

**逐字节搬**：`from` / `at` / 「不可信输入」那句跟着文件走 —— 换个地方它仍然自称外来材料。
**先复制、校验、再删源**：`$DSH_HOME` 与工作区通常不同卷（`rename` 会 `EXDEV`），
而任何早于 unlink 的失败都让消息**留在信箱**（下次照样提示）—— 重复可取，丢失不可取。
**按内容幂等**：落点已有相同字节 = 这次搬运算已完成。

落点用点目录（`.lore-inbox/`）是刻意的：那是**收件方的材料**，不是项目内容 ——
好找、好归档，也不会被当成项目的一部分（顺便好 gitignore）。它**不放在 `work_log/` 里**：
容器的门禁、索引与编号是技能层的事，而一条消息**不是一篇记录**。

**不做**（与规矩 2 的"不要在它上面加语义"一致）：发送（`put`）、正文检索、归档、
写记录（`--into-record` 是技能层的事）、批量删除。CLI 仍是**写与归档**的权威。
（2026-10-17 重新明确：插件工具层可以给 `put` 做一层**薄包装**（`--text` / `--file`），
但写路径仍然只有 `put` 一条 —— 见下。）

### 2026-10-17 重新明确：同/跨分治、发送工具、广播**不做**

用户提了一版五点（发给谁 / 怎么发 / 发什么 / 怎么收 / 广播有没有必要；原话照录在
`work_log/logs/input/信箱提议-重新明确-20261017.md`）。逐点定下来：

① **搜索对话：默认同工作区；跨工作区在 2026-10-18 起改为"显式 `scope: "all"` 可查、只读、带标注"。**
原口径（2026-10-17）是"同工作区可以，跨工作区不行"：规矩 2 挡的是"**另一个**工作区的会话清单"
—— 那等于对方的工作标题与时间线。同一工作区里的会话是**用户自己的**，不存在这个侦察面，
所以"选定范围 → 搜索 → 返回标题"只在**同工作区**这一档成立。**投递**仍只到**工作区**粒度：
发件方表达"给哪个工作区"，**放进哪个会话由收件方决定**（规矩 3）。确实要人肉挑一个跨工作区的
目标时，走界面由**用户**挑，模型只负责发给被挑中的那个工作区。
（"随对话内容自动改标题"那类插件帮不上这里：标题正是从**内容**推出来的元信息。）

**已落地（2026-10-17）**：`worklog_memory` 的 `sessions` 操作列**同工作区**的会话（标题来自
`sessionQuery.readTitle`）。边界取**调用方 Agent 的 `cwd`**，`workspace` 参数不参与判定
（模型能随手填一个别的路径）；拿不到 initiator 就**拒绝**，不猜。

**2026-10-18 用户补充：跨工作区可查、但必须显式且带标注。** `sessions` 增加 `scope`：

- `scope: "workspace"`（默认）：行为与 2026-10-17 完全一致，只列调用方工作区。
- `scope: "all"`：**只读**地列出本机各工作区的会话，每行标注所属工作区
  （`@<工作区名>`，名字取 `workspaceRegistry.list()` 的 `title`，缺省退回目录名）。
  发送侧不变 —— `send.session` 仍只接受**本工作区**会话，跨工作区投递只到工作区粒度。
  侦察面因此从"默认不列"变成"默认不列、显式一步才列，且始终带归属"；
  这是用户在自己的多工作区机器上明确要求的能力。
  设置页的「允许跨工作区查看会话」（高级页，默认开）是它的开关：关掉后 `all` 被拒绝。

**已归档的会话不列**（2026-10-17 补）：宿主的 `sessionController.list()` 返回的是完整语料
（live + persisted），归档集合在 `workspaceRegistry.archivedSessionIds` 里、由界面那侧隐藏；
工具自己再按这份集合过滤一次 —— 用户归档一个对话，就是不想再在任何"可选项"里看到它。
**`scope: "all"` 也照样过滤。**
**宿主没有 registry 时静默不过滤**（老版本 / 极简宿主）：工具描述里写明了这一点，免得有人以为
它一定排除了；跨区行的工作区名在那种宿主上退回会话目录名。

② **发送工具：做 `put` 的薄包装，但"递文件"必须装进信里。** 工具层给 `--text`（短）/
`--file`（长）两条，写路径仍然只有 `put`（CLI 是权威）。**不许把文件直接放进对方目录**：
`from` / `at` / 「不可信输入」头部要跟着正文走（规矩 5 的机械痕迹），"文件"在协议里是
**信的正文**，不是旁路。收件侧 `.lore-inbox/` 已经是"整份文件进工作区"，两侧对称。

**已落地（2026-10-17）**：`send` 的 `text` / `file` 两条参数（长正文 >8 KiB 自动落临时文件
再走 `--file`，避开 Windows 命令行上限）。实现是起 `journal.py inbox put` 子进程 —— **不重写
一遍格式**，于是"写路径只有一条"是真话而不是纪律；子进程的 stdio 走**文件**而不是管道
（受限沙箱里 Node 的 pipe 会 `EPERM`，实测过）。

③ **字段只加两个**：稳定 `id`（去重 / 幂等）与可选 `thread`（来回）。`from` / `at` /
「不可信输入」已经覆盖了"时间与来去"。**别再堆字段** —— 正文永不进提示词，字段的收益
只体现在 `list` 的元信息里。

**已落地（2026-10-17）**：`id` = 正文的 sha256 前 16 位（同一条正文重投得到同一个 id；
它**不是防篡改**，只是"哪一条"的标签），`thread` 只在真回信时写，不塞空字段；
`inbox list` 与 `inbox take` 都显示这两个字段。

④ **两种收法都已实现**（主动模式 / 被动计数 + `worklog_memory` 的 `inbox` 取件）。
主动模式 2026-10-17 实装：收件方在**自己的工作区**跑 `inbox subscribe` 授权（写
`<记忆根>/inbox-subscriptions.json`，里面有一个固定收件会话 id 与已推送条数）；**沙箱会话里
CLI 写不了记忆根**（workspace-write 挡在 `~/dsh-lore-memory` 外，实测 `Permission denied`），
所以同一件事也给了工具入口 `worklog_memory` 的 `subscribe`（`active: false` 撤销）——
边界是**调用方 Agent 的 cwd**，发件方替别人开不了。发件方 `send` 带 `to` 时走
`sessionController.create` → `resolveAgent` → `agent.followup(createUserMessage(...))` →
`sessions.flush`（**与 `dsh-schedule` 同一条投递路**；不用给界面用的 `prompt`，那条要过
附件与上传绑定），推的是**不含正文**的提醒；每成功一条 +1，到 40 条换一个新会话（规矩 6）。

**`create` 必须给 `workspaceId`，不能只给 `cwd`**（2026-10-17 真机补）：两者都把会话建在正确
目录里，但只有 `workspaceId` 那条会走 `workspace.attachSession(sessionId)`，把会话挂进
`workspace.sessionIds` —— **界面就是按这份名册分组的**。只给 `cwd` 建出来的会话在磁盘上一切
正常，却会在对话列表里显示成**「未分组」**（真机实例：`session-3e2f…`「跨工作区来信提醒处理」）。
所以送达前先按路径在 `workspaceRegistry.list()` 里找那个工作区；**有名册但找不到就拒绝主动
送达**（信仍在共享信箱），而不是造一个野会话。

**没有名册的宿主退回 `cwd`**（轮十四复核补）：headless / 嵌入宿主根本没有"分组"这回事，
`create({ cwd })` 完全够用 —— 不该因为一个纯界面问题让它们失去主动送达。区分两种情形：
服务**不存在** → 退回旧行为；服务**存在但路径不匹配** → 才拒绝。

`send` 不带 `to` 时只投不推，答案会说明"信在共享信箱里、任何工作区都能取"。**代价照旧**：
主动送达会在收件人不在场时花额度，所以默认关、只有收件方能开。

**发件边界（2026-10-17 复核补）**：`send` 的 `workspace` 必须是**本会话自己的工作区**（它是
发件人身份，不许冒充别的目录 —— 与 `sessions`/`subscribe` 同一条边界），`file` 必须落在该
工作区内（`realpath` 比较，软链接也挡）。否则模型可以把任意本地文件整份复制进跨工作区信箱。
**授权表的读-改-写没有跨进程锁**：插件在写回前会重读一次，`active` 已被撤销或收件会话已换
就**不写**（撤销不能被旧快照复活）；剩下的窗口很小，已知、接受，记在这里。

**同工作区的对话可以点名（2026-10-17 加）**：`send` 多一个可选 `session` —— 只允许**自己
工作区里**的会话（`to` 必须等于自己的 cwd；用 `sessionController.inspect` 校验归属，按
`archivedSessionIds` 排除已归档）。跨工作区仍然只到工作区粒度 —— 对方的会话清单是侦察面。
送达走同一条 `create({workspaceId, sessionId})` + `followup`，所以"往某个对话发提示"与
"往工作区收件会话发"没有第二套机制。

**同工作区转送不走公共区域（2026-10-17 定）**：`to` 就是自己的 cwd 时，信**直接**写进
`<工作区>/work_log/.lore-inbox/`（容器里的点目录，门禁与索引都不扫它；没有 `work_log/` 时
退回工作区根下的 `.lore-inbox/`），**不进**共享记忆根的信箱，也不受共享信箱的条数/总量
上限约束（单条大小上限照旧）。写盘仍走 `journal.py inbox put --outbox DIR` —— 格式只有一份。

**读后要处理（2026-10-17 定）**：直投信在落点旁边有一份 `.pending.json`（"发了、还没办结"）。
办结有两条路，都会把信**归档**到 `<工作区>/work_log/logs/inbox/` 并从待处理里去掉：
① **回执**：回信时 `send` 带 `thread = 原信 id`（这叫"读过了、办完了"）；
② **显式标记**：`worklog_memory` 的 `inbox` 带 `message = <文件名>`（这叫"处理掉"）。
没办结的会**一直列在 `inbox` 的待处理里**（`[direct]` 行），提醒文案也写着"未处理的会一直列在
待处理里" —— 这就是"读后应当被处理"的机械判据：文件不会悄悄堆在收件夹里。

**显示：来源标记是 `inbox-notice`，不是 `user`**。消息仍然是 **`user/message`（user 角色、
不可信输入）**，也**不是** developer/system —— 规矩 4 不动；变的只是 `source.kind`：界面按
来源分类，`kind === 'user'` 画成**用户气泡**，其他 kind 画成「触发本轮」的通知卡（与后台任务、
定时任务同一套 `TurnTriggerNode` 外观）。用户 2026-10-17 明确要求后者。

⑤ **广播：不做（2026-10-17 定）。** 四条理由：

- 它要的语义位置已经被**全局记忆**占了 —— 那是"所有工作区都该知道的共性问题"的容器，
  而且是**唯一无条件注入**的通道（收件人不用去"取"）。广播 = 寿命更短的记忆 + 收件人写成 everyone。
- 它撞了信箱的核心不变式**单消费者**：`take` 的语义是"复制 → 校验 → **删源**、按内容幂等"，
  而 N 个读者谁都不能删源 ⇒ 另一套生命周期（按时效过期）、另一套计数语义、**第二个存储类**。
  这不是加个 `all` 标签的事。
- **信任方向反了**：消息是不可信外部输入、正文不进提示词。广播是"信任最低 × 触达最广 ×
  没有可追责的发件方关系"，而注入面每宽一分，代价翻一倍。
- 它要解决的痛点其实是"**一次发给多个收件人**"，而那不需要新机制：一条命令发 N 封 **1:1** 的信
  —— 每封各有收件方、各有计数、各有生命周期，规矩 1–5 一条都不用改。

真要做的那天，四条最低要求：`to: all` **显式标注**、**永不自动拉起**、计数行**分开报**
（「N 条（含 M 条广播）」，免得收件人误以为在跟自己说话）、**源文件永不因取件而删除**。

⑥ **独立性要可断言，不能靠假定。** "不同对话与工作区互不串"应当有一条**能跑**的反向验证
（A 工作区的信箱正文永不进 B 的上下文与落点）—— 同一天 `wl/0116` 那次事故的教训：
隔离被假定、没人验，九轮全绿也能把数据写到别人家里。

**已落地（2026-10-17）**：`tests/audit-inbox-delivery.mjs` 断言四件事 —— 列表与取件都
不返回正文；主动提醒里没有正文标记；取走的信只落在取件方的工作区（别处没有 `.lore-inbox/`）；
`sessions` 列不到别的工作区。它跑在隔离记忆根上，A/B 两个假工作区都只活在那次运行里。

## 十二、升格为技能

**分界**：一条事实进记忆；**一套过程**进技能。全局技能落在 `<DSH_HOME>/skills/`
（已被 `dsh-skill-filesystem` 的 `dshHome` 扫描覆盖，**不需要发明机制**）。

三条件**同时**满足才够格（`promote suggest` 报候选，但**不自动打包**）：

1. **是一套过程**：有触发条件 + 步骤 + 验证方式，读者能照着做。
2. **已真实执行过**：至少一个工作区里**按它做过并成功**。
3. **有重复需求**：被多个工作区引用，或同一工作区多次命中。

**唯一硬规则 —— 技能只许"教"，不许"管"。**

- 可以写"这类问题怎么诊断"（教）
- 不许写"你必须先做 X"（管）

理由不只是谦虚：**一份强势的技能会与实际项目冲突，而冲突的结果通常是技能被无视
或被关掉** —— 连带它本来有用的部分一起废掉。

**验收：必须带可跑自测。** 升格时同时交一个最简验证（fixture + 一条命令），
且该自测**能变红能变绿**。依据是本工作区的既有事实：技能自测的 308 条断言正是把技能
从"一份看起来对的文档"变成"能验的东西"；而技能的暴露面（名字+描述进每个会话目录）
是这些产物里最大的，坏了没人知道代价最高。
