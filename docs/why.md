# 为什么要做这个（初衷、不变量与现状对照）

> **状态**：2026-09-30 立项留档。
> 这份文件回答的是「**必须保证什么**」，与 `*-spec.md`（回答「怎么设计」）分工不同 ——
> 规格是对实现的约束，这份是对**目标**的约束。**改实现前先看这里。**

## 一、初衷（用户原话，两次，逐字）

### 1.1 第一次

> 对于一个需要长期维护，可能经常性切对话甚至换 agent 的项目文件夹，记录各阶段问题（要求）、
> 处理方式、结果（产出，经验教训）以及下一阶段要做的，保证在工作区切对话甚至交由
> **没有该 skills 的 agent** 接手时能快速了解状态，理解经验教训（如果需要）并接手工作；
> 记录的历史内容可供查阅。

同日的动机补充：

> 当时搞了个东西预计要搞很久，怕有遗漏信息，就要求建立 work log 文件夹。

### 1.2 第二次（同日稍后，两条补充）

> **粒度与覆盖**：这种东西很难硬性限制，但是另一方面作为一个面向工作区或者面向项目的设计，
> 一个项目文件夹（一个工作区有一个（工作区本身就是项目文件夹）多个项目文件夹
> `…\project_of_agent\embeding try`）里的 work log **至少要保证对所处项目文件夹的较详细记录**。
>
> **交接的定位**：交接本身相对于开发周期来讲是低频行为，也没必要专门硬性要求交接，
> 主要是做到**不管哪个 agent 过来看都能看明白情况**。

### 1.3 说明（留档时补的 —— 原话太笼统，不补就会各人各读）

- **粒度是「项目文件夹」，不是「工作区」。** 一个工作区里可以有多个项目文件夹，各记各的；
  工作区本身也是一个项目文件夹。实例：`embeding try` 下 7 个项目文件夹，**6 个各有一个
  `work_log/`**（`1_minimind_main` / `2_multi_attention` / `3_param_block` / `5_diffusion` /
  `6_block_wiring` / `7_jev_decision`），工作区级另有一层 `_lessons/` 放**跨项目共享**的经验
  —— **项目级记过程，工作区级共享经验**。
- **「较详细」是底线，不是可以机械判的东西。** 能判的只有"有没有容器""编号连不连"；
  "记得够不够详细"判不了 —— 所以这条**有意不加硬性门禁**，靠使用习惯。
- **交接不是一份文档，而是记录本身的可读性。** 交接低频，不值得为它加仪式（不要求交接产物、
  不要求交接清单）；要做的是让**已经写下的东西**别人来了看得懂。
- **历史可查阅**：记录收口后不改写，被推翻时追加更正；归档只移动 + 改链接，编号不动。

## 二、由此推出的不变量（改实现时不许破）

| # | 不变量 | 靠什么守 | 缺口 |
|---|---|---|---|
| I1 | 容器要详细记录**它所在的那个项目文件夹** | 记录格式 + 每篇一个验证类小节 | 无门禁判"够不够详细"（用户已认可：这类事很难硬性限制） |
| I2 | 记录四段：**问题/要求 → 处理方式 → 结果 → 下一步** | 入口字段（触发/范围/结论）+ 验证小节 + 遗留 + 滚动待办 +（可选）`目标.md` | "下一步"散在三处：待办 / 各篇遗留 / 目标表 |
| I3 | **没有该 skill 的 agent** 来了也能看懂 | 约定：项目根 README 指向容器 | **无门禁**（`check` 不审项目根）；台账大时状态块埋在文件后段 |
| I4 | 经验可复用、可追证 | `lessons` 每条必须带来源（写入硬拒 + 门禁） | 存量条目的"没写来源"判定是整文件粗筛 |
| I5 | 历史可查阅 | `outline` / `search` / `archive`（链接重写 + 死链自检）/ `prune`（只搬不删）/ `split` | —— |
| I6 | 技能层不知道 DSH 存在（可独立跑） | 四层依赖单向（`plugin-spec.md` §一） | —— |
| I7 | 不为「交接」加仪式 | 2026-09-30 明确 | —— |

## 三、这份文件的来历与已知缺口（不假装没有）

- **初衷原文从来没有被留档过。** 构建期（2026-09-13 ～ 15）技能自己**没有过程记录** ——
  `README-MIGRATION.md` 里写着「构建期没有单独建 journal / lessons」；源工作区那 211 篇记录里
  最早一篇是 2026-08-22 的环境备忘，不是需求。这份文件是**事后**依据用户 2026-09-30 的复述
  重建的，不是当时的原始文本。
- **I3 目前靠自觉**：约定写在 SKILL.md 的初始化流程里，但 `check` 完全不看项目根 ——
  漏写那一行指针不会红。2026-09-30 讨论过的取舍：不加硬性门禁（用户：「这种东西很难硬性限制」）。
- **成熟容器的门禁降级**：记录 ≥ 5 篇的容器整批按旧记录判，所以**新写的记录缺验证小节只报 INFO**。
  2026-09-30 起 `check` 每次会打印一行说明这件事（照旧不改计数与退出码）。
