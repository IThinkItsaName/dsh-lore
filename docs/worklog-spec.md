## 零、三个语料（这是全部分歧的来源）

| 语料 | 位置 | 篇数 | 命名 | 台账 |
|---|---|---|---|---|
| **原型** | `D:\Program Files (x86)\dsh_from_github\work-log` | **207** | **编号** `NNN-slug.md`（1–209） | 背景 + 分阶段索引表 + 归档说明 |
| **当前实践** | `...\project_of_agent\embeding try\<线>\work_log` | **71** | **日期** `YYYY-MM-DD-*.md` | 五条线里四条 0 字节；一条是背景 + 关键事实 |
| **另一项目** | `D:\Program Files (x86)\comfy\journal` | 30 | **编号**（日期在文件名里） | 索引 + `## 当前状态` 块 |

**两种命名约定同时存在，而且都在用。**

- 编号式：原型 207 篇（编号 1–209）+ `comfy` 30 篇 = **237 篇**
- 日期式：`embeding try` 71 篇（68 篇带日期）

**关键历史事实**：原型里**没有 `journal.py`，也没有 `project-work-log` 技能** ——
那 207 篇是手工写的。**所以编号是你自己的原生约定，技能是后来把这个实践书面化的。**
日期式则是另一条线（`embeding try`）后来长出来的。

### 原型周边的三份附属物（都已核实）

原型工作区（`dsh_from_github`）里除了 `work-log/`，还有：

| 位置 | 内容 | 与体系的关系 |
|---|---|---|
| `lessons/`（7 文件 / 78 KB） | 6 分册 + 索引：构建环境 / WPF-UIA / dsh 契约 / 验证方法论 / 事故档案 / **99 阶段复盘** | **体系的第二层，成熟形态**。每条 `症状 → 根因 → 做法 + 来源`，用 `wl/NN` 回指 |
| `_archive/2026-09-15-worklog-stage/` | 只有 `README.md` | 记录体系自身的一次阶段归档 |
| `notes/`、`_trials/` | 随手笔记、试验别的启动器 | **与体系无关**，不要当作记录层 |

`lessons/README.md` 本身写清了使用方式，值得作为规格的范本：

> **动手前**：查对应分册的"易错点"清单。
> **排查时**：先查事故档案，症状对得上就直接看根因与修法。
> **新增经验**：先写进分册（一条 = 症状 + 根因 + 正确做法 + 来源），再在 `work-log` 里留完整过程记录。
> **阶段收口**：写进 `99-retrospectives.md`，**不要**另建 SUMMARY 类文档 —— 同一批数字维护两份就是漂移的源头。

其中两条真正有价值，规格要吸收：

1. **经验手册是排查入口，不只是归档。** "动手前查易错点、排查时先查事故档案" ——
   `lessons/` 被当成**先读的东西**，不是写完就放着。这一条比任何格式规定都重要。
2. **禁止平行文档。** "同一批数字维护两份就是漂移的源头" —— 这正是本次对话反复踩到的病
   （`journal/`→`work_log/` 的路径漂移、两份技能文档说反话）。规格里要继续保留这条禁令。

**「先写经验还是先写记录」的顺序无所谓** —— 只要两处都在、且能互相追溯即可。
`lessons/README.md` 建议"先分册后记录"，`embeding try` 实践里相反，都可行。
**规格不规定顺序**，只要求：经验条目的来源记录必须真实存在（现有校验项）。

### 「篇号 vs 变更集」的真相（推翻了一处官方说法）

原型根 `README.md` 里写着：

> `work-log/` | **过程记录**（**编号与变更集对应**：背景 → 核查证据 → 方案 → 实施 → 验证）

**实测：从来不对应。**

| 检查 | 结果 |
|---|---|
| `变更集` 号等于篇号 | **0 例** |
| 有 `变更集` 字段 | 26 / 162 |
| 写 `变更集：无` | **146** |
| 最近 14 篇的对应 | 篇 198 → 变更集 175；篇 207 → 变更集 **182**（差 25） |

两个计数器**独立发展**：篇号 1–209，产品仓变更集 1–182。

这解释了技能**铁律 3「篇号与迭代号分开」**的由来 —— 那条铁律正是为了**防止**有人以为它们对应。
原型看起来已经踩过这个坑（否则不会写进铁律）。

而 **146 篇写「变更集：无」**说明一件更重要的事：
**这份记录远不止追踪代码变更** —— 工作区整理、取证与复核、环境与资产变动都记。
它是**工作记录**，不是**变更日志**。

> 这意味着：**不能简单说哪个是"主"、哪个是"兼容"。** 两者都是真实约定，
> 规格必须**同时支持**，而不是把一方降级。§十一 把这个选择交给你。

## 一、为什么要改

现在技能（`project-work-log`）的格式规格取自原型那套（编号 + 集中台账 + 固定六段式 + 机械门禁）。
但**用户当前的实践已经分叉**：新项目（`embeding try`）用的是日期式 + 自由结构 + 分散状态。

拿技能去量 `embeding try`，结果如下：

| 技能**要求**的 | `embeding try` | 说明 |
|---|---|---|
| 标题 `# NNNN · 标题` | **0 / 71** | 编号从未被使用 |
| 入口 `日期：YYYY-MM-DD` 字段 | **0 / 71** | 日期写在 **H1 里**，不是单独字段 |
| 文件名带日期 `YYYY-MM-DD-*.md` | **68 / 71** | 这才是实际约定 |
| 有验证类小节 | **54 / 71（76%）** | **这条实践是认的**，只是形式更宽 |
| `## 当前状态` 块 | **0 / 5 条线** | 状态写在每篇开头的引用块里 |

而在原型上，技能的要求**基本都符合**（207 篇全是编号式）。

> **所以技能并不是"错"的，它是为原型那套写的，只是没有覆盖后来长出的日期式。**
> 本规格要做的是**让两套都被认得**，而不是推倒重来。

> 实测方法：按文件名、H1、标题级小节逐一匹配；词表用技能自己的同义词集
> （验证/复核/检查/评审/结果/证据/评估/确认/实测/审查 + 实验/判定/评测）。
> 复现脚本见 `logs/tests/measure-real-corpus.mjs`。


## 二、实测出来的两个事实

### 事实 1：结构是"长出来的"，不是模板套出来的

`embeding try` 的 71 篇里出现了 **409 个不同的 `##` 标题**，而**最高频的那个也只出现 2 次**：

```
2x  结果      2x  结论      2x  实验设置      2x  判定      2x  文件      2x  待办
1x  0. 总览   1x  1. 前向每一步（实测形状）   1x  评测设置   1x  3. 训练时数据如何流 …
```

**强行套六段式模板，会把 409 种自然结构压成一种。** 所以本规格**不规定节次**。

> 注意这条只对 `embeding try` 成立。原型那 207 篇**用的是六段式**（背景/事实/方案/执行/验证/遗留），
> 而且用得挺整齐。所以这不是"模板不好"，而是**同一个人在两个项目上用了两种结构** ——
> 规格的答案只能是"都允许"。

### 事实 2：状态放哪，两个语料是相反的

| 语料 | 状态在哪 |
|---|---|
| `embeding try` | **每篇开头的引用块**（`> 状态：… ｜ 工具：… ｜ 产物：…`）；台账里**没有**状态块 |
| 原型 | 台账 `work-log/README.md` 有**分阶段索引表 + 归档说明**，另有 `SUMMARY.md`（后按技能约定取消） |
| `comfy` | 台账有**索引表 + `## 当前状态` 块**（八字段） |

**三种做法都在用。** `analysis.md` 里 P1/P2 两条缺陷（状态块过期、状态块膨胀）**只在集中式上存在** ——
那是原型 + comfy 的形态带来的，不是 `embeding try` 的。

**规格的答案**：状态的位置**由容器自己决定**，工具不强制。
- 台账里**有** `## 当前状态` → 校验它的新鲜度（日期不早于最后一篇）
- 台账里**没有** → 不报错，只报 info 提示"可以考虑加一块"

这样三种形态都过得去，而集中式的过期问题仍然被抓。

## 三、单篇记录

### 文件名 —— 两种约定都认

**编号式**（原型 207 篇 + `comfy` 30 篇）：

```
NNN-<简短标题>.md
```

- 编号 1–3 位（原型用三位，如 `209-workspace-tidy-20260925.md`）
- 编号**单调递增、永不复用**，归档不改号 —— 这条随编号式一起生效
- 日期可写进文件名后缀（`comfy` 的做法）或只写在正文

**日期式**（`embeding try` 68 篇）：

```
YYYY-MM-DD-<简短标题>.md
```

- 日期**必填**，格式 `YYYY-MM-DD`
- 同一天可以有多篇（实测最多一天 **8 篇**），靠标题区分
- **不分配编号**

> 一个容器内**建议只用一种**，混用会让排序与索引变乱。
> 但**工具两种都识别**，且对已存在的老容器不强制迁移（见 §八 渐进原则）。

标题用中文，可含英文/代码词；避免 Windows 非法字符 `\ / : * ? " < > |`。

### H1 标题

```
# NNN · <标题>              ← 编号式
# YYYY-MM-DD <标题>         ← 日期式
```

三种真实写法（都实测存在）：

```markdown
# 209 · 工作区检查与清理                                      ← 编号式（原型）
# 2026-09-06 门控两段式（GateAttention MLM 10k → sim NCE 5k）   ← 日期式（embeding try）
# 2026-09-20 R21：`slot` 悬崖的机制 —— 是超参缩放伪影，不是容量极限  ← 日期式 + 线内实验号
```

> `R21` 这类**线内实验号**是可选增补，实践里只在需要稳定指代时才加、且与日期并存。
> 它是编号式与日期式之间自然长出来的折中 —— 规格**允许但不强制**。

> 编号式的标题**必须**带篇号（`# 209 · …`），否则回指会歧义；
> 日期式的标题**必须**带日期。两者都禁止标题与文件名不一致。

### 入口元信息（建议，可缺）

按容器里已有的风格二选一。

**引用块式**（`embeding try` 在用）：

```markdown
> 状态：**已完成**／进行中／已放弃
> 工具：`<本次用到的脚本或命令>`
> 产物：`<产出的文件或数据>`
```

**字段行式**（原型与 `comfy` 在用）：

```markdown
日期：2026-09-25
变更集：无
触发：用户「检查并清理工作区」
```

字段名不固定，按本次情况选。**新记录建议写，旧记录不要求补。**

### 小节

- **必填**：一个**验证类小节**（标题含 验证/复核/检查/评审/结果/证据/评估/确认/实测/审查/实验/判定/评测 之一，h2–h4 都算）
- **不规定**其余节次的数量、名称、顺序

> 这是本规格最大的松动。旧技能强制"背景 → 事实 → 方案 → 执行 → 验证 → 遗留"；
> `embeding try` 的 71 篇里出现了 **409 个不同的 `##` 标题**，最高频的也只出现 2 次 ——
> 结构是长出来的。强制模板只会让人绕开它。
>
> 原型那套六段式**仍然可用**，只是从"必填"变成"模板之一"。
> 注意这里有个已识别的漏判风险：`评测设置` 这种**只写设置、没有结果**的标题会被
> 误判成"已满足验证要求"。见 §十一 待确认项 1。

### 引用地址

- **编号式**容器：写编号（`wl/209`）
- **日期式**容器：写文件名（`2026-09-06-门控两段式.md`）

**不引入短锚点编号** —— 文件名/编号已经唯一自明，再加一层是多余。

> 两种都失效的情况：跨容器引用。见 §十一 待确认项 3。


## 四、目录布局

**每条线各自一个容器**，互不干扰：

```
embeding try/
├── 1_minimind_main/
│   └── work_log/
│       ├── README.md                    ← 该线的背景与关键事实
│       ├── 2026-08-31-结构梳理.md
│       └── 2026-09-19-脚本参数化与沙箱缓存.md
├── 2_multi_attention/work_log/
└── 3_param_block/work_log/
```

- 容器名默认 `work_log/`；旧名 `journal/`、`work-log/`、`work_log/` 都认（只读，不迁移）
- **不做跨线合并**：五条线是独立课题，合并成一个大容器只会让导航变差

## 五、台账（`work_log/README.md`）

**职责 = 这条线的背景与关键事实**，不是导航索引：

```markdown
# 记录 / Worklog

本文件夹用于记录 <这条线在做什么>。

## 项目背景
- 目标：
- 方案：

## 关键事实（已核实）
- <核实过的、以后会反复用到的结论>

## 目录
按日期记录，如 `2026-08-31-环境准备.md`。
```

- **可选**：文件索引表、滚动待办（没有也能用）
- **不要求** `## 当前状态` 块 —— 状态在每篇开头（见 §二 事实 2）

## 六、经验层（`lessons/`）

保留技能里的这一层，因为它是实践里**没有、但确实有用**的部分：

- 每条结论**必须带来源**（记录文件名），来源不存在就不许写
- 格式：**症状 → 根因 → 做法 → 来源**
- 分册按这条线的实际主题划，不预设

## 七、归档

保留技能的判据，因为它是实践里没有的：

- **判据 = 阶段收口**（某阶段结束、索引不再增长），不用"多少天没引用"
- 动作：移到 `work_log/<stage>/` + 改写全仓链接 + 补归档索引 + 死链自检
- **证据不删**：整理永远是"移走 + 汇总 + 留清单"

## 八、校验（新规格的核心增补）

实践里**没有**机械校验，这是技能能带来的主要价值。校验只做**客观可判**的事：

| 检查 | 级别 |
|---|---|
| 文件名日期格式合法、H1 含日期 | error |
| 有验证类小节 | error（**这是唯一的内容要求**） |
| 记录都在索引表里（若台账有索引表） | error |
| 全库 md 链接无死链 | error |
| lessons 的来源文件存在 | error |
| 缺少入口引用块 | **info**（建议项，不算错） |
| 缺索引表、缺待办、缺状态块 | **info** |

### 渐进原则（重要）

**老记录只报不拦。** 现有 71 篇里有 17 篇缺验证小节，`comfy` 有 30 篇是编号命名。
如果新规格一上来就让它们全部 error，用户会面对一片红，然后学会忽略这个工具。

所以：
- **新写的记录** → 按新规格判 error
- **已存在的记录** → 只报 info
- 判定依据：文件名日期**早于**容器里首个新规格记录（或用一个显式的 `--legacy-before DATE`）

## 九、相对旧技能的变更

**注意**：这里不是"取消编号式"。编号式是**原生约定**（原型 207 篇），必须保留。
变的只是 **从"唯一格式"变成"两种格式之一"**。

| 项 | 旧技能 | 本规格 |
|---|---|---|
| 篇号 `# NNN ·` | **强制** | **编号式容器强制；日期式容器不用** |
| 文件名 | `NNNN-slug.md` | `NNN-slug.md` **或** `YYYY-MM-DD-slug.md` |
| `日期：` 字段行 | 强制 | 建议（日期式可写在 H1 与文件名） |
| 六段式模板 | 强制 | **模板之一**，不强制节次 |
| 中央 `## 当前状态` 块 | 强制 | **容器自选**；有则校验新鲜度，无则不报错 |
| "编号永不复用" | 必修律 | **只在编号式容器里生效** |
| 短锚点编号 | — | 不引入 |
| 机械校验 | 有 | **保留**（这是技能的主要价值） |

## 十、相对旧技能保留的东西

| 保留 | 为什么 |
|---|---|
| 机械校验（死链 / 漏索引 / 来源存在） | 客观可判，人手工做很费劲；三个语料都没这个能力 |
| 验证小节的**明确要求** | `embeding try` 已有 76%，提到 100% 是纯收益 |
| `lessons/` 且**必须有来源** | 原型在用（7 分册）；"结论可追溯"是核心价值 |
| 归档判据与"证据不删" | 原型在用（`archive/` 48 篇）；长期项目的必需品 |
| 编号式全套约定 | 原型 207 篇 + `comfy` 30 篇依赖它 |
| 旧布局只读兼容 | `novle` 30 篇、`comfy` 30 篇、原型 207 篇都依赖它 |
| 精细度档位 | 保留，但默认应重新评估 —— 见 §十一 待确认项 4 |

## 十一、待你确认的分歧点

1. **验证类小节的词表**：本规格把「实验 / 判定 / 评测」也算作验证类（研究类项目常用）。
   但 `评测设置` 这种**只写设置、没有结果**的标题会被误判为"已满足要求"。要不要收紧？
2. **渐进原则的判定依据**：用"文件名日期早于某天"，还是用一个显式的白名单？
3. **跨线引用**：`2_multi_attention` 的结论引用 `1_minimind_main` 的记录时，路径怎么写？
   现在是相对的，归档后会不会断？
4. **精细度默认档 —— 实测数据指向"我改错了方向"**。

   我按 `analysis.md` 的二手指标，把默认档从 `full`（一篇 = 一个可交付单元）
   改成了 `session`（一次会话一篇）。实测三个语料后，**这个改动很可能是错的**：

   | 语料 | 同一天最多几篇 | 平均每篇 |
   |---|---|---|
   | **原型**（207 篇，111 篇有 `日期：` 字段） | **2026-09-13 一天 34 篇** | — |
   | 同上，其它高峰 | 09-23 **25 篇**、09-09 **18 篇**、09-25 **10 篇** | — |
   | `embeding try` | `2_multi_attention` 同一天 **8 篇** | 6.0 KB |
   | `3_param_block` | — | 9.3 KB |

   原型 111 篇分布在 **12 个日期**上，平均 **9.2 篇/天**。

   **一天 8–34 篇是这个体系的正常节奏。** 在 `session` 档下，09-13 那 34 篇会被压成
   **一篇** —— 那不是"更简洁"，那是把 34 个可独立查阅的单元埋进一个文件里，导航价值直接归零。

   **建议：默认档退回 `full`。** `session`/`digest`/`milestone` 保留为可选，
   用于确实低强度、以阶段为单位的项目（写作、调研、运维），而不是研究/开发类密集项目。

   > 这条说明一件更要紧的事：**"记录太多"这个原始诉求，可能从一开始就诊断错了。**
   > 你看到的"多"，是密集实验的正常产物，不是粒度失控。见 §十二。
5. **状态块与分散状态的取舍**：§二 事实 2 说"容器自选"，但这样"当前在哪"就没有统一答案。
   要不要提供一条命令，把最近 N 篇的入口引用块**汇总**成一份只读快照（不改文件）？

## 十二、对原始诉求的重新判断

这次规格工作最初是因为一个抱怨：**"记录是不是过于详细了，导致日志数量过大"**。

实测三个语料后，我认为**这个诊断需要修正**：

| 观察 | 数据 |
|---|---|
| 单篇篇幅 | `embeding try` 平均 **6–9 KB**，`comfy` 平均 **73 行** —— **都不臃肿** |
| 合规率 | `embeding try` 日期 71/71、验证 76%；`comfy` 日期 30/30、验证 30/30 |
| 引用覆盖 | `comfy` **25/30 篇被 lessons 引用过**（83%） |
| 篇数密度 | 一天 8–34 篇，**是密集工作的正常产物** |

**"篇数多"不等于"记录冗余"。** 真正的冗余会表现为：短而无验证、写了没人引、结构空洞。
这三个语料**都不符合** —— 尤其 `comfy` 的 83% 引用率，与 `analysis.md` 里
"127 篇只有 24 篇被引用"（19%）形成鲜明对比。

> **那条 19% 是原型早期的数据。** 引用率随项目成熟自然会升（lessons 沉淀需要时间）。
> 用它来论证"记录太多"，是把一个阶段性现象当成了结构性问题。

**所以本规格不引入任何"让记录变少"的机制**，也不建议再往粗调档位。
要释放的产能不在"少写"，而在"少做无用功"：

1. **机械校验**（死链/漏索引/来源）—— 三个语料全靠人肉，这是真实痛点
2. **渐进校验** —— 老记录不拦，新记录才要求，避免一片红
3. **格式放宽** —— 不再强制六段式，让结构随内容长（`embeding try` 已经在这么做）
4. **`变更集` 降为可选** —— 146/162 篇写「无」，它不该是主字段
5. **经验手册当排查入口用** —— 原型的 `lessons/README.md` 明确要求"动手前先查"，这不是格式问题而是用法问题

**换句话说：这一版的目标不是"写得更少"，而是"写得更省力、记得更可靠"。**
