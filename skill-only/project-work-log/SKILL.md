# 项目长期工作记录 · 无脚本版（project-work-log）

> **来源与免责声明**：本技能的约定与文档整理自作者使用 **DeepSeek Flash 系列模型**处理内容时的常用操作，
> 并**完全由 DeepSeek Flash 系列模型整理生成**（未经人工逐条校验）。
> 使用时请自行甄别，**不保证效果、正确性与适用性**；建议先小范围试用，再按项目的实际情况调整。

## 先说清楚：这一份是什么

这是**没有脚本的版本**，只有文档。

**验证靠人工复核，没有机械门禁。** 结构对不对、日期缺没缺、链接死没死，全靠你自己看。
没有任何工具会拦住你。写坏了没人报错，只会在下次接手时才发现。

所以这份技能**不是**「带工具箱那版的轻量版」。它是另一件东西：**一份靠自觉执行的写作与复核规范**。
它把三层结构、收尾清单、归档判据都写清楚了，但每一道检查都要你亲手做。

**什么时候用这一份**：环境里不能跑脚本——纯聊天界面、别人的 agent 平台、临时机器。
**什么时候别用这一份**：能跑脚本就用带工具箱的版本。那里同样的约定由工具执行，你不用记这么多。

代价说明白：这一份保住的是**方法论**（结构、编号、粒度、复盘的写法），丢掉的是**执行力**（自动改文件、自动查死链、自动过门禁）。

## 这是什么

把「项目里发生过什么、怎么验证的、留下了什么可复用经验」沉淀成**三层、可检索、可复核**的文档体系。
三层同住**一个容器目录** `work_log/`（默认名，可改名），内部各有分工：

| 层 | 位置 | 职责 | 生命周期 |
|---|---|---|---|
| **过程层** | `work_log/NNNN-*.md`（分卷后 `work_log/<YYYY>/NNNN-*.md`） | 一篇记录一次工作（一篇覆盖多少，见下「记录精细度」） | append-only，收口后不改写 |
| **索引层** | `work_log/README.md` | 分阶段索引 + 同主题簇 + 滚动待办 + **唯一**当前状态块 | 每次收尾更新 |
| **经验层** | `work_log/lessons/*.md` | 提炼后的可复用知识：症状 → 根因 → 做法 → 来源 | 持续追加，每条必须有来源 |

记录正文的顺序固定：背景 → 事实 → 方案 → 执行 → 验证 → 遗留。

一句话：**过程留证据，索引管导航，经验可复用**。三层不互相复制内容。

容器里的其他固定位置：归档记录在 `work_log/<stage>/NNNN-*.md`（阶段目录直接建在容器下，
**没有** `archive/` 一层）、旧状态块在 `work_log/STATE-HISTORY.md`、归档索引在 `work_log/ARCHIVE.md`、
日志与运行产物在 `work_log/logs/<来源>/`。完整布局与「日志归位要求」见
[references/conventions.md](references/conventions.md)。

> **领域无关**：这套结构不限于编程。三个标签各自认一组同义词，词表还可以自己扩：
>
> - **迭代**：`迭代 / 变更集 / 批次 / 阶段 / 版本 / 里程碑`（英文 `Iteration / Milestone`）
> - **验证小节**：`验证 / 复核 / 检查 / 评审 / 结果 / 证据 / 评估 / 确认 / 实测 / 审查`
>   （英文 `Verification / Review / Results / Evidence / Tests`）；标题级别 h2–h4 都认
> - **可核对的内容**：命令、数据、引用、样本都算
>
> 各领域的写法：研究项目 `批次：3` + `## 结果`（样本量、结论、反例）；写作项目 `版本：v2` +
> `## 评审`（编辑意见与处理）；软件项目 `变更集：154` + `## 验证`（测试命令与通过数）。
>
> ⚠ 一个标签一个值：写 `迭代：3`，**不要**写 `迭代 / 批次：3`（两个标签并排，读不出来）。
>
> 自己领域的叫法不在表里怎么办：**直接往词表里加**。这是允许的，做法见
> [references/conventions.md](references/conventions.md) 的「词表可以自己扩」。

## 何时用

- 用户说「开始一个新任务」——先确认/建立这套结构，再开工。
- 一项工作 / 一个迭代完成后要「收尾 / 留记录 / 更新台账」。
- 要「总结经验 / 整理踩坑 / 做复盘 / 归档旧东西」。
- 接手一个已有 `work_log/`、`journal/`、`work-log/`、`lessons/`、`docs/` 记录体系的项目，要按既有约定续写
  （旧名 `journal/`、`work-log/` 与顶层 `lessons/` 都能被识别，**只读取、不迁移**）。

## 铁律（先看这 8 条）

1. **先记录、后动手**（方案类）：先写清「要解决什么 + 选项 + 建议默认值」，用户确认后再实施；有疑问先记录，不擅自改。
2. **一篇 = 一次会话**（默认档 `session`；档位可调，见下「记录精细度」）。
   一次会话里做了几件可交付的事，都并进同一篇。只有两种情况另起一篇：
   **一件事跨了多次会话**，或者**它本身足够大、值得单独成篇**。
   纯调研/一次性记录把迭代字段写 `-`。
3. **篇号与迭代号分开**：篇号是文件名/标题/回指用的地址（`wl/NNNN`）；迭代号只写在迭代字段（默认 `迭代：`，也认 `变更集/批次/阶段/版本/里程碑`）。
4. **历史不改写**：收口后不抹旧结论；被推翻时**追加** `## 更正`（日期 / 原结论 / 新证据 / 现结论）。
5. **验证要有可核对的内容**（命令 / 数据 / 引用 / 样本）与结果；没做的必须写明「未覆盖 + 原因」。光说「完成了」「应该没问题」不算验证。
6. **经验必有来源**：lessons 每条带 `（wl/NNNN）`，来源不存在就不许写。
7. **台账只有一个 `## 当前状态`**，字段固定（见下）；换新块时旧块整段剪到 `work_log/STATE-HISTORY.md`。
8. **编号永不复用，归档不改号**；归档只移动文件 + 改链接。

完整约定见 [references/conventions.md](references/conventions.md)；模板见 [references/templates.md](references/templates.md)。

## 记录精细度（一篇 = 什么）

默认档是 `session`：**一次会话一篇**。档位存在台账 `## 当前状态` 的 `精细度` 字段里。
字段随容器走、进版本控制，不需要新配置文件。

| 档位 | 一篇 = | 一次会话的预期产出 |
|---|---|---|
| `full` | 一个可交付的子单元 | 2–3 篇 |
| **`session`（默认）** | 一次会话，或一个可交付成果 | 最多 1 篇；同一会话里的第二件事**追加到同一篇**；只有一件事跨会话、或它本身够大，才另起一篇 |
| `digest` | 一个阶段 / 跨多次会话 | 多次会话并成一篇 |
| `milestone` | 一个阶段收口 | 只留决策与经验 |

档位只决定**要不要另起一篇**，以及可选叙述写多细。**验证要求不随档位放宽**：任何档位下，一篇记录都必须有可核对的验证小节（铁律 5）。

`digest` / `milestone` 还多一条义务：**写明这一轮刻意没有记录什么**，例如
`未记录：本轮的两处配置调整，见提交 abc1234`。粗粒度合并了多轮会话，不写这一句就等于静默丢信息。

怎么切档：

- **在会话里说一句**（临时）：「这次记详细点」/「按阶段汇总就行」→ 本轮按 `full` / `digest` 写。
  口头说的只管这一轮。
- **改台账**（持久）：把 `## 当前状态` 里 `精细度：` 那行的值改成 `full` / `session` / `digest` / `milestone` 之一。
  要留理由就把原因写在同一个值里：`精细度：digest（原因：阶段收口）`。

**精细度只认这四个拉丁值。** 不写别的词，也不要写中文档位名。
台账里没有 `精细度` 这行**不算错**：按默认档 `session` 处理，继续用就行。

## 工作流 A · 初始化（项目第一次用）

1. 先查已有体系：列一遍项目根，找 `work_log/` `journal/` `work-log/` `lessons/` `docs/`，
   以及根 `README.md` / `CLAUDE.md` / `AGENTS.md` 里的记录约定。
   **已有体系就沿用它的命名与编号，不新建平行目录。**
2. 没有则按 [references/templates.md](references/templates.md) 手工落盘（容器名默认 `work_log/`，可改名）：
   - `work_log/README.md`（台账模板）
   - `work_log/lessons/README.md` + `work_log/lessons/01-<topic>.md`（先建 3–5 个与本项目相关的分册）
   - `work_log/STATE-HISTORY.md`、`work_log/ARCHIVE.md`
   - 有日志/运行产物的项目同时建 `work_log/logs/<来源>/`（见下「日志归位」）
   - 在项目根 `README.md` 加一行指向 `work_log/README.md`
3. **自检，自检过了再往下走**（没有工具替你查，这步不能省）：
   - 台账模板里的**示例索引行** `[0001-示例.md](0001-示例.md)` **删掉，或换成真实文件名**。留着就是死链。
   - 台账模板里的示例待办、示例同主题簇同样要删干净。
   - 每个链接都点一遍，确认目标文件真的在。
   - 此时没有记录，索引表可以是空的；空表不算错。
   - 这些文件**都还没有编号记录**：`README.md`、`STATE-HISTORY.md`、`ARCHIVE.md`、`lessons/`、`logs/`
     都不是记录，不要给它们编号，也不要写进索引表。

## 工作流 B · 一项工作（日常）

```
记录 → 确认 → 执行 → 验证 → 收尾
```

1. **记录**：先看档位——读一眼台账 `## 当前状态` 的 `精细度`。
   默认档 `session` 下，**同一会话已有记录就追加到那一篇**，不要新开；
   确实要新开时照「记录模板」建文件，把入口那 5 行先填上：日期、迭代、触发、范围、结论。
2. **确认**：方案、口径、取舍写进记录；等用户拍板（涉及数据/破坏性操作必须确认）。
3. **执行**：小步做、每步可回退；做了什么记进「执行」表。
4. **验证**：用该项目能给出的核对方式（测试、数据、引用、样本、评审），把**依据 + 结果 + 未覆盖**写进验证小节。
5. **收尾**：见工作流 C。

## 工作流 C · 收尾清单（每篇记录都走一遍）

照 [references/conventions.md](references/conventions.md) 的「手工操作规程」逐条做：

1. 记录补齐：`日期/迭代/触发/范围/结论` + 验证小节 + `## 遗留与下一步`。
   档位是 `digest` / `milestone` 时，再加一句「未记录：…」。
2. 台账：索引表加一行；涉及跨篇主题就更新「同主题簇」；滚动待办增删。
3. **状态：更新 `## 当前状态` 的 8 个固定字段**：
   `阶段 / 版本`、`迭代`、`产出`、`核对 / 验证`、`交付物与指纹`、`环境`、`阻塞 / 等待`、`精细度`。
   字段名按台账里已有的写法原样保留 —— 认短名（写「核对」会落到「核对 / 验证」上），不要改成新字段。
4. **经验**：本轮若有可复用结论，写进 `work_log/lessons/` 对应分册，并回填 `（wl/NNNN）`。
5. **复核**：按下面「人工复核清单」过一遍，全过才算收口。
6. **日志归位**：本轮产生的持久日志 / 运行产物放进 `work_log/logs/<来源>/`，别留在项目根。
7. 提交：文档与产物一起提交；提交信息引用篇号（如 `work_log: 0042 ...`）。

### 人工复核清单（代替门禁）

按门禁标准复核时，下面每一条不通过都算**不通过**，不要当成「提醒」放过去：

| 检查 | 看什么 | 不通过的样子 |
|---|---|---|
| 日期 | 记录入口有 `日期：YYYY-MM-DD` | 缺这一行；日期写成「今天」这类相对说法 |
| 验证小节 | 有 `验证 / 复核 / 检查 / 评审 / 结果 / 证据 / 评估 / 确认 / 实测 / 审查` 之一作标题，h2–h4 都算 | 整篇没有验证小节；只有「已解决」 |
| 可核对内容 | 验证小节里有命令、数据、引用或样本 | 只有「测试通过」而不给通过数；只有「应该没问题」 |
| 未覆盖 | 写明没验的部分与原因 | 一个字的交代都没有 |
| 索引 | 新记录在台账索引表里有对应一行 | 记录建了，索引没动 |
| 死链 | 索引表与正文里的 md 链接目标都存在 | 指向不存在的文件；示例行忘了删 |
| 编号 | 篇号连续、不重复；标题 `# NNNN · 标题` 与文件名编号一致 | 断号、重号、标题编号与文件名不符 |
| 状态块 | 全文件只有一个 `## 当前状态`，并且有日期 | 堆了两块状态；状态块没有日期 |
| 新鲜度 | 状态块的日期不早于最后一篇记录的日期 | 状态块比最后一篇记录还旧 |
| 来源 | 每条经验都带 `（wl/NNNN）`，且那个编号真的存在 | 结论没有来源；来源编号写错 |
| 粗档位 | `digest` / `milestone` 的记录写了「未记录：…」 | 粗档位合并且什么都没说 |
| 占位符 | 正文里没有模板残留（`<一句话>`、`TODO`、`<对象>`） | 占位符原样留着 |
| 空小节 | 每个小节都有实质内容 | 标题在，下面空着 |

> **默认档位不是门禁。** 默认档只把问题当「提醒」，不会拦住你。
> **按门禁标准复核时，缺日期、缺验证小节都算不通过。** 自己盯住这两条，它们最容易漏。

## 工作流 D · 归档、瘦身与复盘

- **归档判据 = 阶段收口**（某个阶段结束、索引表不再增长），不用「多少天没引用」这类经验值。
- 归档 → 瘦身 → 复盘，三步都要手工做。每一步做什么，见
  [references/conventions.md](references/conventions.md) 的「手工操作规程」：

  - **归档**（把篇号区间搬进阶段目录）：移动记录文件 → 改写仓库里所有指向它们的链接 →
    逐一检查死链 → 在 `ARCHIVE.md` 补一行。
  - **索引瘦身**：把已经整节归档的索引小节折叠成一行区间，例如
    `| [02-research/](02-research/) | 0027–0045（19 篇，已归档） |`。只动索引，不动记录。
  - **复盘**：照模板生成阶段复盘骨架，填进 `work_log/lessons/99-retrospectives.md`。

- 很久以后，已归档、又没人引用的记录可以**冷存**。顺序是：**先只报告候选** → 得到明确要求才动手 →
  打包留清单 → 原件移出。**绝不删除**。没人明确要求时，连报告都只是报告，不要擅自搬。
- 记录成千上万时按年分卷（移进 `work_log/<YYYY>/`）；`wl/NNNN` 回指不受目录变化影响。
- 复盘写进 `work_log/lessons/99-retrospectives.md`（阶段表 / 成果 / 可复用发现 / 遗留），**不要**另建 SUMMARY 文档到处写同一批数字。
- 铁律：**证据不删**——整理永远是「移走 + 汇总 + 留清单」；搬动后必须自己把链接全查一遍。

## 日志归位（任何产出都要归位）

- **持久日志 / 运行产物一律进容器并分类**：`work_log/logs/<来源>/`，一个来源一个子目录
  （例 `work_log/logs/build/`、`work_log/logs/bench/`）。**别散落在项目根，更别写到项目之外。**
- **测试夹具、一次性样本不是记录**，不进 `work_log/`。
- 日志里**不写绝对机器路径**，只写相对项目根的路径（脱敏后再落盘）。

完整表述见 [references/conventions.md](references/conventions.md) 的「日志归位要求」。

## 反模式（真实项目实测踩过的，别再来）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 台账靠人肉同步、长期不更 | 「当前状态」过期，看板不可信 | 收尾必更状态块，并自己核对新鲜度（状态块日期 ≥ 最后一篇记录日期） |
| **一次会话里每件事都另起一篇** | 记录按「发生了几件事」增长：实测 151 篇里 127 篇从没被 lessons 引用过 | 默认档 `session`：同一会话并进一篇；真要细就把档位改成 `full`，别默默多开 |
| 粗档位合并多轮会话，却不写漏了什么 | 粗粒度静默丢信息，事后无处查 | `digest` / `milestone` 下必写一句 `未记录：…` |
| 当前状态 + 一堆历史状态堆在索引 | 索引膨胀、改一处分多处 | 只有一块当前状态，旧块进 `STATE-HISTORY.md` |
| 有的记录写日期、有的不写 | 无法复核、审计困难（实测 106 篇只有 41 篇有日期行） | `日期：` 必填，按门禁标准复核时缺了就算不通过 |
| 篇号当迭代号引用 | 引用歧义 | 迭代号只写迭代字段，回指一律 `wl/NNNN` |
| README 与 SUMMARY 各写一份数字 | 改一处漏一处 | 复盘并入 `work_log/lessons/99-retrospectives.md`，数字只留一份 |
| lessons 写结论不带来源 | 追不回证据、无法证伪 | 每条带 `（wl/NNNN）`，并确认编号存在 |
| 直接抹掉被推翻的旧结论 | 丢失演进与纠错价值 | 追加 `## 更正` 段 |
| 把软件术语当成通用要求（如「验证必须有命令」） | 研究/写作类项目无法满足，规则被架空 | 验证口径是「可核对的内容」：命令、数据、引用、样本都算 |
| 一次性调研随手建新目录 | 编号体系分裂 | 沿用既有 `work_log/`（或旧名 `journal/`），不编号就写 `迭代: -` |
| 日志、trace、导出文件散在项目根（或写到项目外） | 证据游离在版本控制与备份之外，接手时找不到 | 一律归位到 `work_log/logs/<来源>/`；夹具不进容器；日志只写相对路径 |
| **以为没有工具也能自动查出问题** | 文档看着齐，实际缺日期、死链、漏索引都没人管 | 人工复核清单逐条过；不确定就再读一遍记录 |

## 没有 Python 怎么办

这一份就是为这种情况写的：**直接照上面的工作流走**，不需要任何环境。

- 建结构：照 [references/templates.md](references/templates.md) 手工落盘那四个文件。
- 写记录：照记录模板填入口 5 行，加验证小节与遗留；标题固定 `# NNNN · 标题`。
- 收尾：把「工作流 C 收尾清单」和「人工复核清单」当检查表逐条走。
- 检索导航：用你手上的查找功能（编辑器全局搜索、平台自带的搜索）代替索引工具，用索引表代替快照。
- 整理：归档就是「移文件 + 改链接」（容器根 → `<stage>/`），**先全仓搜一遍链接再改**，改完再搜一遍。

## 环境边界

- 纯文档，无依赖，任何环境都能读。
- 记录文件用 **UTF-8**。用别的编码写中文，别人读出来是乱码，标签也认不出来。
- **中英双语都认**（写入默认中文）：`日期/Date`、`结论/Conclusion`、`触发/Trigger`、`范围/Scope`、
  `迭代/Iteration`（及 `变更集/批次/阶段/版本/里程碑/Milestone`）、
  `验证/Verification`（及 `复核/检查/审查/评审/结果/证据/评估/确认/实测`）、
  `当前状态/Status`、`待办/TODO`、`文件索引/Index` 都能读。
