# 基线分析：一套真实项目的 `work-log/` + `lessons/` 是怎么做的

> 本文件是这套 skill 的**事实依据**。数据由 `scripts/_measure.py` 在一个真实项目上实测（2026-09-13 的快照），
> **文中每个数字都能用 `_measure.py` 重新量出来**（它同时给出条目数、日期/小节覆盖、索引链接与死链、
> 状态块字符数、历史状态块个数、经验引用覆盖等）。读它只为一件事：知道哪些约定要沿用、哪些坑不要再踩。

## 一、基线结构（三层）

```
work-log/                       过程层（append-only，一篇 = 一个变更集/一次会话）
├── README.md                   索引层：分阶段索引 + 同主题簇 + 滚动待办 + 当前状态
├── SUMMARY.md                  项目级复盘（阶段表 / 成果 / 可复用发现 / 遗留）
├── 46-....md ~ 151-....md      在活跃记录
└── archive/                    归档层（按阶段分目录，编号不动）
    ├── README.md
    ├── 01-<阶段>/
    └── 02-<阶段>/

lessons/                        经验层（提炼后的可复用知识，按主题分册）
├── README.md                   分册索引 + 使用方式
├── 01-<主题>.md
├── 02-<主题>.md
├── 03-<主题>.md
├── 04-<主题>.md
└── 05-<主题>.md
```

配套纪律（写在根 `README.md` 与 `lessons/README.md` 里）：
**记录 → 确认 → 实施 → 验证 → 发布 → 台账**；一篇一个变更集；结论沉淀进 lessons 后原文留档。

## 三、做对了什么（沿用）

1. **三层职责分离**：过程（work-log）/ 检索（README 索引）/ 复用（lessons）。三者不互相复制结论：
   work-log 留证据与过程，lessons 留症状→根因→做法，索引只做导航。
2. **编号即事实来源**：文件名编号连续、归档不改号、跨引用用纯编号（`wl/NN`）。
   归档时只改路径不改编号，历史提交信息不追改（见归档索引里的换算表）。
3. **一变更集一篇、收尾更新台账**：把"做了什么"和"怎么验证的"绑在一起。
4. **同主题簇**：跨阶段把同一件事的编号按发生顺序排成一行（如"崩溃与崩溃归因"串起 40→42→61→109→110），
   解决了"一篇只讲一次改动、看不见演进"的问题。
5. **证据优先、失败也留档**：记录里明写"未覆盖/未验证"、自我纠错（`已修正的旧结论`）、事故复盘（分支线事故、批量脚本三次翻车）。
6. **lessons 每条带来源**：`（wl/47）` 这类回指让结论可追证，避免"经验变成无主之谈"。

## 四、实测暴露的问题（本 skill 要修掉的）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| P1 | **台账漂移**：`当前状态` 靠人工同步，容易过期 | 某一篇记录的 P2-7 就是"README 当前状态已过期"；`当前状态` 块 3,508 字符 | 看板不可信，读者要重新核对 |
| P2 | **状态块无限膨胀**：当前 + 3 个历史状态混在同一索引 | 实测 3 个 `历史状态` 区块 | 索引越长越没人读；改一次要动多处 |
| P3 | **格式漂移**：`日期：` 行 61% 缺失、11 篇无验证小节 | 41/106、95/106 | 机器无法校验，检索/审计困难 |
| P4 | **双计数器混用**：篇号 ≠ 变更集号，且"不占号"记录没有显式标记 | 73/106 标题带变更集号 | 引用歧义（`wl/120` 是第 120 篇，不是变更集 120） |
| P5 | **同一批数字维护两份**：`README.md` 与 `SUMMARY.md` 各写一遍 MD5/测试数 | 两文件重叠 | 改一处漏一处 |
| P6 | **索引对记录无覆盖检查**：没有工具证明"每篇都进了索引、每个链接都活" | 目前靠人工体检 | 死链/漏索引只能靠下次全量扫描发现 |
| P7 | **lessons 回指不可校验**：`wl/NN` 打错也无人发现 | 无校验工具 | 结论追不回证据 |
| P8 | **归档判据是经验值**（"最后引用距今 ≥4 天且阶段收口"） | 归档索引里的说明 | 新项目无从照搬，容易随手乱归档 |

## 五、本 skill 采用的结构（相对基线改了什么）

| 主题 | 基线做法 | skill 做法 | 服务的问题 |
|---|---|---|---|
| 层级 | work-log / lessons / SUMMARY 三份文档 | `journal/`（过程）+ `journal/README.md`（唯一台账）+ `lessons/`（复用）；**取消 SUMMARY**，项目复盘并入 lessons 的"阶段复盘"分册 | P5 |
| 状态 | 当前状态 + 多个历史状态堆在索引 | **只留一个 `## 当前状态`**，强制字段模板；旧状态移入 `journal/archive/STATUS-HISTORY.md` | P2、P1 |
| 日期 | 有的写有的不写 | `日期：` 为**必填行**：默认档位判 **WARN**，`check --strict` 才判 ERROR | P3 |
| 验证 | 有验证小节但不强制 | 入口 5 行（日期/迭代/触发/范围/结论；迭代行只写一个标签）+ **验证小节必填**（同为 WARN / `--strict` 判 ERROR） | P3 |
| 编号 | 篇号与变更集号混在标题 | 标题固定 `# <篇号> · <标题>`，变更集号只在 `变更集:` 元数据字段（可 `-`） | P4 |
| 校验 | 无 | `journal.py check`：编号连续、日期/小节必备、链接不死、索引覆盖、`wl/NN` 可回指、状态块唯一且新鲜 | P1、P3、P6、P7 |
| 归档 | 靠"≥4 天"经验值 | **阶段收口即归档**（一个阶段结束、索引表停止增长），并且归档只 move 不改号 | P8 |
| lessons | 5 个分册 | 沿用分册法，条目格式固定为 **症状 → 根因 → 做法 → 来源**；新增"阶段复盘"分册承接 SUMMARY | P7、P5 |
| 工具 | 无 | 见下方第六节：**20 个顶层子命令**（另有 `index sync`/`index compact`/`lesson add` 三个子动作，合计 23 个可执行动作），覆盖「少读 / 少写 / 可校验 / 分析生成 / 可整理」五类 | P1–P8 |

> 保留的核心不变量：**编号不改、历史不改写（更正用追加）、结论必须回指证据、验证必须留下可核对的信息**
> （命令、数据、引用、样本、评审意见都算 —— 见第七节）。

## 六、工具箱（相对基线补齐的能力）

基线全靠人肉读 53 KB 索引、手改状态块与表格。skill 用 `scripts/journal.py` 把这些动作工具化，
按“省上下文 → 省手工 → 可校验 → 增值”四档排列：

| 档 | 命令 | 解决基线里的什么 |
|---|---|---|
| **省上下文** | `brief` / `show` / `search` / `outline` | 基线要读整个 `README.md`（53,620 字符）才知道当前状态；现在 `brief` 一屏给出坐标（实测压缩到 2 KB 内），`show` 只给单篇大纲，`search` 只回命中行 |
| **省手工** | `new --insert` / `status` / `todo` / `index sync` / `lesson add` / `append` | 基线手写索引行、手改状态块、手删待办、手抄经验；现在全部外科式行级编辑，保留 CRLF、支持 `--dry-run`，且 `status --roll` 自动满足“唯一状态块”约定 |
| **可校验** | `check` / `lint` | 基线无任何自动检查；现在 `check` 管结构（编号/日期/验证/死链/漏索引/状态新鲜度/来源可回指），`lint` 管内容质量（占位符、空小节、结论无数字、含糊措辞） |
| **增值** | `stats` / `topics` / `digest` / `retro` / `export` | 基线没有的分析与生成：语料节奏与合规率、同主题簇建议、交接摘要、阶段复盘骨架（自动汇总未完成项）、JSON/CSV 导出 |
| **可整理** | `archive` / `index compact` / `split` / `prune` | 基线整理靠人肉搬文件、手改链接；现在四个命令覆盖归档 / 索引瘦身 / 分卷 / 冷存，全部 `--dry-run`，搬完自动验死链，且**只搬不删**（`prune` 默认只报告） |

在基线项目上跑这些命令的结果：`check` **0 error / 121 warn**（warn 全部是基线遗留的格式漂移，
恰好印证第四节的 P3；放宽验证关键词后比首测的 132 条少了 11 条误报），`stats` 给出日期跨度与引用覆盖，
`topics` 能自动捞出跨篇复现的标识符（文件名、编号、专有名词一类）。
工具自测：`scripts/_selftest.py` **95/95 通过**（含 CRLF 保真、"只改目标行"、非编程场景、整理能力、
英文标签、`status --set` 短名解析、非 UTF-8 拒写、归档后链接仍有效，以及
「模板落盘后能被自己的门禁接受」等断言）。

> 设计取舍：不引入第三方依赖（无 CJK 分词、无 YAML 解析），因此 `topics` 自动模式只认 ASCII 标识符，
> 中文主题用 `--keywords` 指定；记录入口用固定 5 行而非 YAML front-matter，换来零依赖与人类可读。

## 七、领域无关化（从"软件项目"推广到通用项目）

基线 `work-log/` 是一个软件项目的记录，措辞天然偏软件：迭代叫"变更集"、验证要求"可复现命令"、
执行段表头是"文件 / 改动"。这些词对研究、写作、设计、运营类项目是障碍。

skill 的泛化做法：**不改结构，只把词汇与口径放宽**，并且不引入配置文件（保持零依赖、零配置）。

| 维度 | 软件专用（基线） | 通用做法 | 兼容范围 |
|---|---|---|---|
| 迭代字段 | `变更集：N` | 写入默认 `迭代：N` | 解析时同时接受 `变更集 / 批次 / 阶段 / 版本 / 里程碑` |
| 验证小节 | 只认 `## 验证` | 任一"验证类"标题 | `验证 / 复核 / 检查 / 评审 / 结果 / 证据 / 评估 / 确认` |
| 可核对内容 | 必须有可复现命令（反引号） | 命令、数字、链接任一即可 | `lint` 的 `_checkable()` |
| 执行段表头 | 「文件 / 改动」 | 「对象 / 改动」 | 只是模板默认值，可随意改 |
| 状态块字段 | 分支/HEAD、构建、测试 | 阶段/版本、迭代、产出、核对 | `status --set` 可任意加键 |

验证方式（已实测）：自测里加了一条**非编程记录**——`批次：3` + `## 结果` + 数据、完全没有命令——
`check --strict` 与 `lint --strict` 均通过；同时基线项目（用 `变更集` 别名）仍 **0 error**。
自测由 34 项增至 **57 项**（后续补的整理能力与英文标签用例计入）。
> 注：上面这句是当时（0.1.1）的记录。0.2.0 又补了数据安全、幂等、文档一致性等断言；
> **当前规模以脚本实际输出为准**（`_selftest.py` 末尾会自动核对文档里出现的数字，
> 写死了就会报 FAIL）。刻意不在文档里写死当前项数，免得每加一条断言都要改一处。

> 取舍：没有做按项目自定义的词表配置（`config.json`）。别名表已覆盖常见叫法，需要时改 `journal.py` 顶部的
> `K_ITER_ALIASES` 与 `VERIFY_WORDS` 两个常量即可；保持"零配置"比多一个需要维护的配置面划算。
